##### 1. إصلاح مشكلة إرسال الصور في واتساب المتخفي (Bot Mode) - Race Condition
**التأريخ:** أبريل 2026  
**الملفات المتأثرة:** `main.js` (السطور 1811-1920, 1663-1675)  
**الأولوية:** 🔴 حرجة - تؤثر على إرسال المستندات للإدارة

**المشكلة:**  
عند إرسال صورتين متتاليتين عبر واتساب (الأولى للموظف والثانية للمدير)، كانت الرسالة الأولى تُرسل بنجاح (صورة + نص)، لكن الرسالة الثانية تُرسل كنص فقط بدون صورة.

**السبب الجذري (Root Cause):**  
- **Race Condition** بين عملية لصق الصورة (`Ctrl+V`) وعملية واتساب الداخلية لتعبئة النص من URL
- عند تحميل URL مثل `https://web.whatsapp.com/send?phone=XXX&text=YYY`، يقوم واتساب بتأخير زمني لتعبئة النص في حقل الإدخال
- النظام كان يلصق الصورة بسرعة قبل اكتمال تعبئة النص
- عندما يُعبأ النص لاحقاً، كان يقوم بمسح معاينة الصورة (Image Preview) واستبدالها بالنص فقط
- المشكلة تتفاقم عند إرسال رسائل متعددة لأن الحالة (State) لا يتم تنظيفها بين الإرسالات

**طريقة الإصلاح (3 طبقات حماية):**

**أ) تحسين آلية الانتظار الذكية (Smart Polling) - `main.js` السطور 1825-1852:**
- زيادة عدد المحاولات من 20 إلى **40 محاولة**
- التحقق من **استقرار النص** (لا يتغير) لمدة 300ms إضافية
- إضافة logging لتتبع حالة النص

**ب) زيادة أوقات الانتظار - `main.js` السطور 1861-1868:**
- انتظار قبل لصق الصورة: من 400ms → **600ms**
- انتظار بعد لصق الصورة (لظهور المعاينة): من 2000ms → **3000ms**
- إضافة **فحص معاينة الصورة** قبل الإرسال للتأكد من وجودها

**ج) إعادة تحميل الصفحة بين الرسائل - `main.js` السطور 1900-1913:**
- إعادة تحميل WhatsApp Web بعد كل رسالة
- ضمان **نظافة الحالة** (Clean State) للرسالة التالية
- انتظار 2000ms بعد إعادة التحميل

**د) زيادة وقت الانتظار في Queue - `main.js` السطور 1663-1675:**
- للرسائل مع صور: **6000ms** (بدلاً من 4000ms)
- للرسائل النصية فقط: **4000ms**

**النتيجة:**  
✅ الموظف يتلقى: صورة + نص  
✅ المدير يتلقى: صورة + نص  
✅ لا مزيد من Race Conditions  
✅ إرسال موثوق ومستقر للرسائل المتعددة

## ⚡ تحسينات الأداء والاستقرار — مايو 2026

هذا القسم يوثّق إصلاحات **البطء، الشاشة السوداء، وتجميد الواجهة (لا يستجيب)** على الأجهزة الضعيفة (مثل Intel Celeron J1900، 4 أنوية، 8GB RAM)، مع الإبقاء على **واتساب وعملياته كما هي** دون تعديل منطق الإرسال.

### 1. الشاشة السوداء عند التفعيل / تسجيل الدخول

**الأعراض:** النافذة تبدو سوداء و«لا تستجيب» عند فتح التفعيل أو تسجيل الدخول.

**الأسباب التي عُولجت:**
- النافذة كانت مخفية (`show: false`) بخلفية داكنة حتى `ready-to-show`.
- استدعاءات متزامنة ثقيلة في Main Process (`wmic` لمعرف الجهاز، `reg query` للترخيص) في كل تشغيل.
- صفحة `login.html` كانت تحمّل `script.js` الكامل قبل إظهار النموذج.
- Firebase يبدأ مبكراً ويثقل الجهاز عند الفتح.

**ما تم تنفيذه:**

| المنطقة | الإصلاح | الملفات |
|---------|---------|---------|
| الترخيص | حفظ `deviceId` في الكاش — بدون `wmic` في كل تشغيل | `licensing/license-manager.js` |
| السجل | تخزين مؤقت لنتيجة `reg query` (60 ثانية) | `licensing/license-manager.js` |
| التجربة | تخزين مؤقت + قراءة واحدة في `getPublicInfo` | `licensing/license-manager.js` |
| IPC | `license-get-info` و `evaluate-access` عبر `setImmediate` | `main.js` |
| Firebase | أول مزامنة بعد **20s** (45s على الأجهزة الضعيفة) | `licensing/license-manager.js` |
| النافذة | إظهار فوري على الأجهزة الضعيفة؛ `ready-to-show` | `main.js` |
| login | إزالة تحميل `script.js` الثقيل؛ فحص ترخيص مؤجّل | `login.html`, `login.js` |
| activation | معرف الجهاز من الكاش ثم تحديث في الخلفية | `activation.js` |

**متغير بيئة (شاشة سوداء / GPU ضعيف):**
```bat
set MISTER_CASHER_SAFE_GRAPHICS=1
```
ثم تشغيل التطبيق. يعطّل تسريع GPU على التعريفات الضعيفة.

### 3. قاعدة البيانات — سرعة دون تجميد الواجهة

**الملفات:** `main.js`, `db-helper.js`, `dashboard.js`, `pos.js`

#### أ) حفظ غير متزامن (لا ينتظر القرص)
- `db-write-full`: يحدّث الكاش فوراً ويعيد النجاح، والكتابة على القرص في **طابور خلفي** (`_writeDbAtomicQueued`).
- `db-save-order`, `db-save-product`, …: لا تنتظر انتهاء الكتابة قبل الإرجاع.
- `broadcastDBChanged` مؤجّل بـ `setImmediate` مع debounce أطول على الأجهزة الضعيفة.

#### ب) قراءة خفيفة (بدون تحميل القاعدة كاملة)
| IPC / دالة | الاستخدام |
|------------|-----------|
| `db-read-day-closures` / `dbReadDayClosures()` | قائمة سجلات الإقفال فقط |
| `db-read-day-closure-detail` / `dbReadDayClosureDetail()` | تفاصيل الورديات عند «عرض» |
| `db-read-slice` / `dbReadSlice(keys)` | لوحة القيادة، إقفال اليوم — طلبات/مرتجعات/مصروفات فقط |
| `db-update-order` / `dbUpdateOrder()` | تعديل طلب في POS بدون `dbRead` + `dbWrite` كامل |
| `db-append-day-closure` / `dbAppendDayClosure()` | إقفال يوم دون نسخ القاعدة كاملة عبر IPC |

#### ج) ضغط سجلات إقفال اليوم (تصغير `pos_database.json`)
- الملخص في `day_closures` **بدون** مصفوفة `shifts`.
- تفاصيل الورديات في `day_closure_details[id]`.
- هجرة تلقائية عند التحميل: `_migrateDayClosureStorage()` (مؤجّلة 12 ثانية على الأجهزة الضعيفة).
- `dashboard.js` — `confirmCloseDay` يستخدم `dbAppendDayClosure` عند التوفر.

**الملفات:** `day-closures.html` — بحث بـ debounce 300ms؛ هجرة `day_closures` مرة واحدة فقط؛ إزالة سجلات تشخيص.

### 6. التنقّل السريع — معطّل (مهم)

**الملف:** `nav-fast.js` (كان يُفعَّل تلقائياً على الأجهزة الضعيفة)

**الهدف الأصلي:** فتح الصفحات من كاش HTML دون إعادة تحميل `script.js`.

**لماذا عُطّل:**
- صفحات مثل **سجلات الإقفال** و **هنقرستيشن** تعتمد على `<style>` مضمّن في `<head>`.
- التنقّل السريع كان ينسخ محتوى `.app-container` فقط **بدون** التنسيقات المضمّنة → ظهور **نصوص بدون تصميم** وتعطل فتح بعض الصفحات.

**الوضع الحالي:**
- `nav-fast.js` — stub معطّل (لا يعترض الروابط).
- `script.js` — `localStorage.setItem('mc_fast_nav', 'off')`.
- خيار «التنقّل السريع» — **أُزيل من الإعدادات**.
- التنقّل العادي: **تحميل كامل للصفحة** (مستقر + متزامن مع القاعدة عند كل فتح).

### 10. توقعات واقعية

- **مستقر ومتزامن:** نعم، بعد تعطيل التنقّل السريع.
- **فوري 100% على كل عملية:** لا — قاعدة JSON كبيرة + جهاز ضعيف = ثوانٍ محدودة عند فتح صفحات ثقيلة أو حفظ ضخم.
- **إغلاق الصفحات عند الانتقال:** تلقائي (نافذة واحدة + استبدال الصفحة).
- **فتح فوري جداً عند العودة:** لا حالياً — مقايضة الاستقرار مقابل السرعة حتى يُبنى تنقّل سريع يدعم CSS المضمّن لجميع الشاشات.
